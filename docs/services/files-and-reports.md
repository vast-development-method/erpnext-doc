# Files and reporting

## Attachment identity and access

An attachment is a site record with its own identity, owner, privacy, URL, folder and optional parent type, name and field. Local bytes and attachment records have separate lifetimes. Multiple records can refer to the same bytes. A remote reference has no local content digest. A folder cannot carry a file URL. On insert, a parent type with a missing parent name is cleared together with the parent field. A valid attachment reference ordinarily requires write permission on the target. A site can restrict creation of public files to its system managers.

When an existing private resource is referenced, normalize its local URL first. Resolve private file records at that canonical address. For ordinary reuse, the site administrator, an owner of one matched record, or an actor with authorized read on at least one matched record passes the reuse gate. Absent matching rows allow processing to continue through the other validations. A resource reused by one authorized parent and one inaccessible parent must not expose metadata from the inaccessible parent.

The file-specific controller grants read/select for public files and handles authenticated owners and explicit supported shares. For a linked file, create/write/delete fall back to write on the referenced document. Other requested actions fall back to parent read. When the target is missing or its module cannot be loaded, this fallback denies access. The outer role/record dispatcher and field restrictions still apply as applicable. Listing also has its own conditions covering ownership, sharing and parent scope. Exercise list and direct access independently.

Moving a local file between public/private locations checks source existence and destination collision before changing the address. Register a full-rollback action to reverse the move. Update linked file records and the parent's attachment field only if it still contains the old URL. Do not overwrite an intervening parent choice. On a fresh file insert the rollback handler cleans up the new blob subject to shared-content handling. A savepoint rollback alone does not run this compensator.

## Prepared results

| Stage | Decision or effect |
|---|---|
| Resolve | Resolve a custom report to its reference report and apply selected column/filter metadata. Require access to the report, reporting rights on its referenced document type and an enabled report. A declared Link filter used in an ordinary run requires read or select on its referenced value. |
| Submit | Check report access before creating the preparation record. Persist owner, report, canonical filters and queued status. Produce its name and enqueue the worker after commit. Use configured timeout or 1,500 seconds. Enqueue is a new request for work. The queued-status discovery service can find an existing request. |
| Run | Mark started with worker job identity in a separate commit. Execute using the preparation owner's identity argument for report filtering. Store structured result with column metadata in a private compressed attachment. Mark completed with end time, or persist error and end time if generation fails. Notify the owner on completed/error, with realtime publication after commit. A worker that runs to completion may still have produced a report whose business status is error. |
| Lookup | Canonicalize filters by parsing supplied text and serializing with sorted object keys and compact separators. A search for work in flight selects queued/started records by report, exact normalized filters and session owner. Automatic lookup of the most recent processed result selects completed **or error** by report, normalized filters and owner, newest creation first. A newer error therefore supersedes an older success in this lookup. |
| Direct retrieval | An explicit result identifier follows a separate permission path. The download service checks read on the preparation record. Its controller considers accessible report names with administrative exceptions. Automatic owner-scoped selection does not by itself make every direct download owner-exclusive. Evaluate effective role and record rights separately. |
| Stop/expire | Stop requires write on the prepared record and a worker identity in the current site's namespace. A successful stop sets cancelled. An already inactive job leaves status unchanged by this path. The stale sweep changes **started** records created strictly more than six hours earlier to error. Its clock is creation time, even after a long queue delay. |
| Return | Decompress the stored result for use. A missing attachment prevents successful download. Return a useful failure to a reader without exposing stored diagnostic tracebacks. Preserve column types, tree rows and totals in the durable result. |

For a financial report, prepare the same date range as two actors with different company restrictions. Verify each automatically selected result against a synchronous run as its owner using identical ledger data. Supply filters in a different object-key order and verify that equivalent keys still match. Include a newer result with error and an old started job exactly at the six-hour threshold. Separately verify direct access to a preparation record under the selected effective permissions after role changes; record access and row contents are distinct observations.
