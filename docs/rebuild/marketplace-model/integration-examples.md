# Three marketplace integrations at their ERP boundaries

These examples follow a payment amount, a cost center and a stock movement through the extension that owns each decision. Each example uses the publisher's pinned source. The [application catalog](README.md) locates additional declarations and tests for the same integration.

## Banking — from payment terms to a SEPA order

A submitted Purchase Invoice with a status other than Paid can supply scheduled installments to a SEPA Payment Order. The mapping accepts an optional set of Payment Schedule row IDs. An omitted set selects all eligible rows, while an empty set selects none. A row is eligible only when its outstanding amount rounded to two decimals is positive. Each generated payment keeps the source document type, invoice ID and schedule row ID. The recipient is the supplier unless both the business-trip employee and the employee-payment flag are populated. A company bank account defaults from enabled company accounts, preferring a default. The mapping returns a payment order for further processing. Transmission to the bank is a separate operation. [Purchase Invoice mapping](https://github.com/alyf-de/banking/blob/bb40082ac9f3948f5f501a511f38af322fa8d5fc/banking/custom/purchase_invoice.py#L20)

For a selected installment, sum non-cancelled SEPA Payment amounts on the same invoice **excluding the current schedule row**. This includes drafts. Cap the installment by the greater of zero and invoice outstanding less that sum. If a discount date exists and the execution date falls on or before it, multiply the capped amount by one minus the percentage discount and round to the schedule row’s outstanding precision. If the row no longer exists, its calculated amount is zero. A linked order status update selects the installment using its preserved row identity. [Cap, discount and covered amount](https://github.com/alyf-de/banking/blob/bb40082ac9f3948f5f501a511f38af322fa8d5fc/banking/custom/purchase_invoice.py#L164)

| Scenario, assuming two decimal places | Expected |
|---|---|
| Invoice outstanding 100.00, another row covered by 30.00, selected row outstanding 90.00, discount 2%, execution on the last discount date | Eligible base 70.00, resulting payment 68.60 |
| Same inputs, execution one day later | Payment 70.00 |
| Same inputs plus an existing non-cancelled payment for 68.60 on this same schedule row | Recalculation still returns 68.60 on the discount date |
| Other rows already cover 110.00 against the invoice outstanding of 100.00 | Payment 0.00 |
| Invoice is fully paid or still a draft | The mapping fails its invoice admission check |

## Utility billing — resolve the cost center on each service request line

Under the Item Price approach, a request needs a company and at least one active requested property. For each row, keep an existing cost center and skip rows already submitted, meter rows and rows with no item. Pick an explicitly requested property on the row first, then the sole requested property, then the sole requested property whose service item matches the row item. With several candidates and no unique match, the row stays unallocated. [Row attribution and assignment](https://github.com/navariltd/utility-billing/blob/7a03323904c8885d466f16b5da523a3d71fd3403/utility_billing/utility_billing/utils/cost_center.py#L195)

Try the property's cost center, then the selling-line default supplied by ERPNext for that item and company. Accept a candidate only when the candidate cost center belongs to the request company. On synchronizing the property's own service item, fill a missing company Item Default or add its company row. An existing selling cost center is preserved, and the item cache is cleared after saving. This affects both the immediate allocation on the request and the future default on sales documents. [Company validation and fallback](https://github.com/navariltd/utility-billing/blob/7a03323904c8885d466f16b5da523a3d71fd3403/utility_billing/utility_billing/utils/cost_center.py#L146) · [Company-specific item synchronization](https://github.com/navariltd/utility-billing/blob/7a03323904c8885d466f16b5da523a3d71fd3403/utility_billing/utility_billing/utils/cost_center.py#L80)

For acceptance, give two requested properties A and B different cost centers and the same service item. A row explicitly naming A takes A's center. A row with only the shared item stays blank. A manually allocated row keeps its center. A row naming A whose configured center belongs to another company may take the item’s usable same-company fallback. [Source test declarations](https://github.com/navariltd/utility-billing/blob/7a03323904c8885d466f16b5da523a3d71fd3403/utility_billing/utility_billing/tests/test_request_item_cost_center.py#L99)

## Warehouse item group rules — enforce source and destination on a transfer

A global Stock Settings flag enables the rule. Hooks attach the same validation to save and submission for Stock Entry, Purchase Receipt, Delivery Note, Sales Invoice, Purchase Invoice and Stock Reconciliation. A sales or purchase invoice with stock updates disabled exits early. For a Stock Entry, inspect both source and target warehouses for every item with an identifiable group. For the other document types inspect the row warehouse. An active rule belongs to the company and warehouse pair and lists the permitted item groups. A missing rule permits the item. The validator accumulates row-level violations and raises one combined error. [Document hooks](https://github.com/ahmedyousef96/warehouse_item_group_rules/blob/c33f3fc5557aa3bcfeb1f31f91eab54bc95c1afb/warehouse_item_group_rules/hooks.py#L11) · [Validation and rule selection](https://github.com/ahmedyousef96/warehouse_item_group_rules/blob/c33f3fc5557aa3bcfeb1f31f91eab54bc95c1afb/warehouse_item_group_rules/rules.py#L15)

For acceptance, transfer one item in group Tools between two warehouses. Give the source an active rule allowing Tools and the destination a rule allowing only Food. The result contains one violation for the destination and row 1. If neither warehouse allows Tools the aggregate contains two violations on the same row. A non-stock sales invoice with that item bypasses both checks. The source uses the same error path when a rule fails on save or submit. [Aggregated rejection](https://github.com/ahmedyousef96/warehouse_item_group_rules/blob/c33f3fc5557aa3bcfeb1f31f91eab54bc95c1afb/warehouse_item_group_rules/rules.py#L167)
