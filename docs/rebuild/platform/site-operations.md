# Application composition and recovery

## Effective metadata and extension precedence

Resolve installed applications and their configured order for the site. Ordinary effective metadata adds site fields, applies property overrides, builds field lookup caches, sorts fields, resolves valid stored columns, replaces permissions with configured custom permissions where applicable, and adds links and actions. Special framework definitions use a limited initialization path to avoid recursive metadata construction. A schema exported from a clean installation must identify its application revisions and site customization profile. Importing a customized invoice with a new required dimension needs the corresponding effective definition before posting.

For a standard type, resolve the base business controller. If multiple applications replace it, the last registered replacement wins and must conform to the original type's contract. Additional behavior extensions are ordered in reverse registration order ahead of the selected base. Cooperative delegation can invoke the next behavior; an extension can also terminate dispatch. With replacements R1 then R2 and extensions A then B, the effective precedence is B, A, R2, original ancestry. This establishes lookup order, not a guarantee that every participant runs. A site-defined custom record takes the generic tree or ordinary path earlier in this controller resolver.

Registration has different collision rules per capability. When two automation action providers publish the same action type, registry construction rejects the duplicate. Treat this differently from last-replacement-wins. Record effective types, field overrides, providers, exposed operations, execution rights and required dependencies before promoting a site's configuration.

## Install and evolve one site

| Boundary | Observed sequence and meaningful output |
|---|---|
| Install eligibility | Resolve app dependencies first. Require an available app. An already-installed app is a no-op in the normal mode. A non-foundation install requires the system manager. A before-install handler returning false stops that install path. |
| Fresh schema | Register module definitions for the added app, synchronize its record types and initial permissions, then register it as installed. The foundation can create its own module records only after its storage exists. Navigation-only modules also need a definition. Synchronize portal menu, initial patch state when configured, post-install hooks and fixtures. |
| Update entry | Select the site and check required services. Acquire the site migration lock. Clear stale metadata and initialize module map and tracking. Concurrent attempts must not publish contradictory effective definitions. |
| Pre-schema | Register newly declared modules before hooks. Execute installed applications' pre-migration hooks. Multiple controller replacements generate a warning. |
| Schema | Run pre-model updates, synchronize schema, then run post-model updates. This order allows different transformations to reference the appropriate schema. |
| Post-schema | Synchronize schedules, missing sequences, optional fixtures, standard items, dashboards, customizations, languages, deferred writes, orphaned definitions and related entities, portal navigation and version history, then invoke post-migration hooks. |
| Finalize | Teardown executes even after a phase failure reached inside the protected sequence. Clear caches, retain touched-table evidence, optionally queue rebuilding the search index and publish version-update notification. A notification or a queued reindex alone cannot prove all phases succeeded. |

Each decorated migration phase commits on success and attempts rollback on an exception; nested schema operations, patch routines and external resources can establish narrower durability boundaries. Treat the update as restartable, with distinct records for completed changes and for business availability. A later-phase failure does not imply that prior phases were rolled back. The blueprint describes current installation and evolution semantics without prescribing historical patch code for a clean rebuild. ## Backup and restore boundaries

The full backup generator handles a database dump, site configuration, public files and private files. A database-only mode can skip the two file archives, and table inclusion/exclusion can yield a partial database. An existing recent set can be reused unless forced. On a fresh generation the path takes the database dump, copies the configuration and optionally archives files, with optional encryption. These are successive steps. Timestamp proximity does not establish one atomic snapshot across the database and both file stores. The restore path restores the database before extracting whichever public and private archives were supplied. A successful database restore does not establish that all attachment bytes or encrypted business credentials are usable. [Backup selection](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/utils/backups.py#L124-L209) · [Restore](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/commands/site.py#L220-L325)

**Rebuild acceptance policy.** Record generation identity, component sizes and digests, source revision, site, table scope, file inclusion and key references in an integrity manifest. This is a proposed recovery standard. In an isolated restore, select known submitted sale and purchase vouchers, verify balanced book entries, re-read an authorized private attachment, confirm that another company restriction still excludes its records, and reconcile the number and statuses of previously in-flight work items. Keep external side effects isolated during the exercise. Reject a completeness claim if a required private archive, key or table is absent. Record recovery point and time from observed evidence, without inferring them from backup frequency.
