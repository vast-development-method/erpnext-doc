# Rebuilding a configured site

Two sites can run the same application commits and give different answers for the same document name, user roles and requested operation. In the worked procurement profile, a stock observer can read order `PO-041` at the coast site. The same role has no Purchase Order access at the inland site. A buyer can read the inland order while its tender decision reference remains restricted to a purchasing manager. Approving the inland order leaves the coast order in draft.

The sources establish the precedence and behaviors below. The app names, companies, roles assigned to example actors, rule limits, prefix values, test records, JSON exchange format and compile procedure are design fixtures. They exercise a slice of the system and can be populated with different production identities. The profile is an interchange specification for a rebuild. An actual site export requires its own adapter and credentials stay in their own protected store.

For the worked projection a common fixture adds `custom_tender_ref` immediately after the ordinary supplier field. A second common fixture changes its label. At the inland site a later installed app supplies another label fixture. Its opted-in customization bundle subsequently sets the final label and casts the permission-level text `"1"` to integer level one. The [compiled projections](effective-sites.json) retain all source steps and the winning value. On the coast site, the field remains at level zero with the common fixture label. The same field identity carries each site's historical values across a label change.

The synthetic layering has one customization bundle per app and one winning setter per attribute. For a production conversion, capture the final effective model together with the app packages, site-local rows and optional skipped imports. Where multiple unsorted bundle files affect one key, record the actual winner or flag an unresolved source conflict. Treating all site-admin edits as an unconditional final layer can disagree with a later fixture reload.

## Workflow, authority and naming

Capture rows for users, roles, applicable company restrictions, permission levels, shares and owner-based grants separately. The examples have no shares or custom controller restrictions. A full evaluation also considers other fixed and child links, optional strict treatment of blank links, per-field exemptions and the requested operation. Check the row before selecting fields the actor may read. Translate tenant-specific identifiers within the selected site's namespace. [Company and linked-record permissions](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/permissions.py#L353) · [Field-level access](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/model/meta.py#L745) · [User permission guide](https://docs.frappe.io/erpnext/user-permissions)

The active workflow owns its selected state field. When missing, the workflow creates a hidden link to Workflow State with allow-on-submit and no-copy enabled. During workflow update, existing blank state fields can be initialized to the first configured state of the corresponding structural status. In this scenario both sites store a draft with a validated company-currency amount. Eligible transition listing requires a saved document, read permission, current state, role and satisfied condition. The execution path reloads the persisted document, selects the action and applies the self-approval rule. A manager who owns the order can see the action in the transition list and still receive a refusal when applying it. Here 10,000.00 is within the rule and 10,000.01 exceeds it. A successful draft-to-submitted transition runs the normal business submission. Workflow authorization alone cannot validate invalid accounting or quantity inputs. [Workflow metadata update](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/workflow/doctype/workflow/workflow.py#L40) · [Discovery and execution](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/model/workflow.py#L45) · [Owner rule](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/model/workflow.py#L307)

For a fresh ordinary order in this profile, naming rule priorities are distinct. The high-priority company-specific rule gets first chance, followed by a general rule. On match the reference reads that rule's counter for update, constructs the prefix and assigns the next padded number. Counter identity follows the rule at the site. Different sites can issue the same textual identifier independently. Preserve counters separately from fixture templates when importing business data. The sequential acceptance cases exercise independent allocation. Testing simultaneous writers and rollback requires a transactional execution environment. [Rule priority](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/model/naming.py#L236) · [Rule allocation](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/core/doctype/document_naming_rule/document_naming_rule.py#L56)

## Schema and workflow dependencies

Resolve each import, form, report and valuation rule against the effective item schema before activation. The company filter and workflow currency field are required by both purchasing examples. Integer `Item.production_capacity` measures capacity. Boolean `Item.use_serial_no_wise_valuation` selects a valuation method and has its own default and display condition. Neither can satisfy a dependency on the other. Refuse a dependent configuration when its required field or type is absent. [Item declaration evidence](../model/delta/erpnext-stock-01.json) · [Schema dependency fixtures](compatibility-cases.json)

For a queued submit or cancellation, acknowledge admission separately from commitment of the requested state and its ledger effects. If a document is returned, project only fields the actor may read. A void response supplies no evidence of posting. Capture the eventual job result, persisted state, ledger effects and response fields separately. [Dispatch evidence 1](https://github.com/frappe/frappe/blob/5921915ad69a1f557cad9dfe6bca8a2cb947bb08/frappe/model/workflow.py#L119) · [Dispatch evidence 2](https://github.com/frappe/frappe/blob/199a0385c00e572664a099a57a00be6ce7404eeb/frappe/model/workflow.py#L120)

## Reproduce and qualify

From the repository root, rerun the compiler in verification mode. The optional schema pass uses a Draft 2020-12 validator.

```sh
python3 docs/rebuild/configuration/compile.py
python3 docs/rebuild/configuration/compile.py --schema
```

The checked-in tests validate the two projections and run the ordered cases with independent in-memory state. A live differential run still needs two separately initialized sites, the equivalent installed app/fixture configuration, validated order lines, and serial plus concurrent callers. Compare effective metadata after installation, repeat migration and a site-local edit, then compare actual query results, transition replies, committed documents, downstream vouchers and numbering after rollback. Record each fixture skip or ambiguous precedence before treating the configured site as equivalent. [Platform acceptance](../platform/verification.md) · [Record model](../model/INDEX.md)
