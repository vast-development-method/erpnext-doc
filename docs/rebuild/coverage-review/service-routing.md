# Incoming call, agent transfer and service history

An incoming call can change its receiving employee while retaining the provider call ID and the links to a contact, customer or lead. A service operator needs to reconstruct who was called, who could receive the on-screen alert, who recorded the outcome and where that outcome will appear. The number matching, shift lookup, transfer event and timeline each have their own decision.

| Event | Decision and business effect |
|---|---|
| Configure coverage | A communication medium has a disabled flag, employee-group time slots and an optional catch-all group. Each row needs a later end time on the same day. The separate incoming-call handling schedule also rejects overlapping slots on the same weekday and accepts adjacent intervals. Persist weekday and group identity independently of the operator’s language. | Find eligible users | For an enabled medium, compare local weekday and time with both endpoints inclusive. Collect groups from all matching slots. A catch-all applies only when no slot matches. Keep active group members with a user ID. A slot whose group has no active user returns no users even if a catch-all is configured. A missing medium argument or disabled record suppresses the alert. [Group and time lookup](https://github.com/frappe/erpnext/blob/886ab6ae187244e7f1b852393384ab6019d56264/erpnext/crm/doctype/utils.py#L20-L61) |
| Create the call log | For an incoming call use the caller's number to locate contacts and leads, and the destination for the receiving employee. For an outgoing call use the destination for contact and lead matching. Add typed links and customer links through contacts, preserving the first populated customer on the header. Validation removes duplicate dynamic links. An incoming popup goes to the intersection of eligible users and employees matching the called number. | Transfer an ongoing call | On an existing incoming call, a new destination causes the receiving employee and user to be updated when there is a match. A changed destination with a new nonterminal status sends the missed event to the previous agent set and recomputes the incoming popup. The rule depends on how a provider represents a transfer. [Status transitions](https://github.com/frappe/erpnext/blob/886ab6ae187244e7f1b852393384ab6019d56264/erpnext/telephony/doctype/call_log/call_log.py#L78-L104) |
| Finish the call | A transition from a nonterminal status into No Answer, Completed, Busy or Failed sends the ended event to users matching the **previous** destination, even if a shift has just ended. Changing from one terminal state to another does not emit that transition again. The literal Cancelled status is absent from this terminal set. ## Handover example

On Monday, Group A covers a medium from 08:00 to 12:00 and Group B from 12:00 to 16:00. At exactly noon the popup lookup includes **both groups** because both bounds are inclusive. If A and B each have one eligible employee but the called number belongs only to A, only A receives the initial popup. At 12:01 the same call is transferred to B while still ringing. The previous destination receives the missed event, the new destination receives a popup if B is eligible, and the persisted receiver becomes B. Completing this call closes B’s popup. These combined observations form a derived acceptance case. The recorded reference tests cover the constituent schedule, transfer, event and recipient decisions. [Reference executions](reference-tests.md)

Keep the call, recipient, source-party link and submitted call-type identifiers stable when an operator switches language. Store a summary in the language in which the agent entered it. A translated work queue may display the same call to a second operator; its language does not confer access to the recording or summary.
