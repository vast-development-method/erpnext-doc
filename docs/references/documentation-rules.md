# Documentation rules

## Scope and terminology

Use comprehensive full names for business concepts, identifiers and machine-readable keys. Avoid acronyms and source product or implementation names. The required navigation filename and machine-readable file extension are repository format conventions; the preserved license is not rewritten. Do not replace a precise concept with a vague generic label simply to avoid an abbreviation.

Distinguish the source record identity, the neutral concept, a projected value and a proposed replacement policy. Neutral names must remain stable after publication. If two source concepts appear similar, compare their fields, lifecycle, calculations, permissions and side effects before combining them.

## Behavioural rule template

For each consequential rule, state its purpose; authoritative inputs; defaults and configuration; preconditions; calculation or decision order; precision and tolerance; persisted effects; state transition; financial and quantity consequences; failures and warnings; cancellation behaviour; and acceptance examples. Attach precise source artifact identifiers and line ranges wherever the rule is source-derived.

Do not reproduce source code, large source comments, executable source-language expressions or source product documentation. Write independent explanations and neutral data facts. A digest-only expression records the presence of logic but does not specify that logic; report that limitation rather than count it as semantic coverage.

## Mathematics

Define every operand, currency or unit, sign convention, valid range and rounding point. Specify zero-denominator behaviour, negative and return cases, boundary inclusivity and residual allocation. Separate a displayed rounded amount from a stored intermediate when they differ. State whether an example is transcribed as factual test inputs, independently derived, or proposed.

Every numerical fixture must have an exact expected answer and the governing policy. Arithmetic checks are useful but do not replace source execution or financial reconciliation.

## Evidence levels

Use structural inventory for mechanically enumerated declarations. Use source reviewed for manually interpreted controller or test behaviour with a cited span. Use independently checked example for arithmetic verified outside the source runtime. Use reference executed only for a recorded run against the pinned reference and configuration. Use replacement executed only after the independent implementation has passed the scenario.

A source function name, comment or test name alone is not evidence that all branches were reviewed. Unexamined behaviour, source discrepancies and missing optional dependencies must remain visible. Never mark a capability complete solely because a generated file exists.

## Changes and consistency

Maintain navigation links, source references, structured catalog validity and cross-domain terminology. A calculation change must update its worked cases and dependent financial effects. A state change must update service contracts, screens, permission expectations and acceptance cases. A record change must update relationships and persistence notes.

Retain the repository license unchanged. Keep source archives, research scripts, temporary files and external implementation assumptions out of the deliverable.
